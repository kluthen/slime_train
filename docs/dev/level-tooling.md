# Level-design toolkit: the tools (chunk LD1)

How a level is authored, where its files are, how the game and the tools
find it, and what each tool does. The level-design rules themselves are in
`specs/level-design.md` (rules 1 to 22); the test level's design is in
`specs/levels/test/README.md`. A tutorial for level designers built on
these tools is `docs/level-design/` (chunk LD, part 2).

## Two ways to author a level, one for the real level

A level is a Godot scene built only from the components in
`src/components/` (D6: no per-level scripts). There are two ways to make
that scene:

- **Hand-placed in the Godot editor** (recommended for the real level,
  `levels/01/`). Open `levels/<id>/level.tscn`, add component scenes
  (`src/components/*.tscn`), draw terrain, loop segments and routes back as
  `Path2D` curves, and set the properties in the inspector. The components
  are `@tool`, so the greybox shows while you edit. This is how level
  content is meant to be made: what you see is what the game loads, and no
  code stands between the designer and the level.
- **Generated by a script** from tables of points (the test level:
  `tools/greybox_test_level.gd`, built on the builder helpers in
  `tools/level_builder/`). Good for a level whose numbers are the design
  (the test level's positions are given in screens in its README) and that
  is regenerated as the design changes. A re-run overwrites hand edits, so a
  level is generated **or** hand-edited, not both.

The two meet in the **scaffolder** (`tools/new_level.gd`): it generates a
skeleton with the builder helpers once, then refuses to touch the level
again. From there the level is edited by hand. The skeleton is a start,
not the level's design.

Whichever way, the result is checked the same way: the level-rules checker
(`tools/check_level.gd`) and the level's own test script.

## A level's files

```
levels/<id>/
  level.tscn            the level scene (root: Level, src/components/level.gd)
  fixtures/             named starting points for test mode
    fresh.fixture.json  the level as new (no save)
    <name>.fixture.json + <name>.json   a fixture with a save
tests/e2e/levels/
  test_level_<id>.gd    the level's generated test (not for the test level,
                        whose tests are hand-written in tests/e2e/)
```

Nothing else: no script inside `levels/<id>/`. The level's save is
`user://saves/<id>.json` (`SaveStore`, one file per level).

## How a level is found and loaded

By ID, by convention: `LevelCatalog` (`src/level_catalog.gd`) maps `<id>`
to `res://levels/<id>/level.tscn` and its fixtures to
`res://levels/<id>/fixtures/`, and lists the levels by scanning `levels/`
for folders holding a `level.tscn`. There is no list to register a level
in: creating the folder is the registration.

Choosing a level is for test mode, the tools and the tests only (debug
builds). v1 ships one level and the player never chooses one: a normal run
of a debug build loads the test level, as before; a release build has no
level choice at all (test mode is refused there, `TestModeGuard`).

- Test mode: the run's `"level"` (default `"test"`), or `--level=<id>` on
  the command line. Fixtures are looked up in that level's `fixtures/`.
- The tools: `--level=<id>` (default `test`).

## The tools

Every tool runs headless from the project root, takes `--level=<id>`
(default `test`) where a level is involved, says what to fix when it
refuses, and exits non-zero on a problem.

| Tool | Command |
|---|---|
| Rules checker | `godot --headless --path . -s res://tools/check_level.gd -- --level=<id> [--rule=N[,M...]] [--fast] [--json]` |
| Scaffolder | `godot --headless --path . -s res://tools/new_level.gd -- --id=<id> [--sections=N]` |
| Fixtures | `godot --headless --path . -s res://tools/make_fixture.gd -- [--level=<id>] [--list] [name ...]` |
| Level report | `godot --headless --path . -s res://tools/level_report.gd -- --level=<id> [--json]` |
| Play a level | `godot --path . -- --test-mode --level=<id> --seed=1 [--fixture=NAME] [--at=<stable id>\|x,y]` |
| A level's test | `tools/test.sh -gdisable_colors -gselect=test_level_<id>` |

### The level-rules checker

`tools/check_level.gd` on top of the library `tools/level_check/`
(`LevelChecker`). For every rule of `specs/level-design.md`, 1 to 22, it
reports one status:

- `PASS`: checked by code, nothing wrong. A `manual:` line under it says
  what part of the rule code can't judge.
- `FAIL`: with findings, each naming the stable ID and the x in screens,
  and what to do.
- `MANUAL`: nothing to check by code; the `manual:` line says what to look
  at.
- `N/A`: the rule doesn't apply to this level (why is given).

A `load` line comes first: the level's load errors (other than stable-ID
ones, which are rule 20's). Output:

```
check_level: level test (version 1): 3 sections, 200 base slimes
load     PASS    The level loads
rule 1   PASS    The loop can be travelled with no input at all
         note: ...
rule 22  FAIL    ...
         - s2.sleeper.15 (x 9.97): it rests on Terrain/Dip2Hollow, which overhangs the loop ...
         manual: ...
check_level: 21 PASS, 1 FAIL, 0 MANUAL, 0 N/A, 21.0 s
```

`--json` prints one object instead (`level`, `version`, `fast`, `load`,
`results`, `counts`; each result `rule`, `title`, `status`, `findings`
(`id`, `x`, `text`), `manual`, `notes`). Exit code: 0 when nothing fails, 1
when a check fails, 2 when it can't run (bad arguments, unknown level).

`--fast` skips the behaviour runs (about 0.3 s instead of about 20 s on the
test level): the laps of rules 1 and 2 and the ways back of rule 7. Without
it:

- **Rules 1 and 2:** in every gate state (each section as the loop first
  reaches it), a lone size-1 train slime, every other slime taken out, laps
  the whole loop with no input; with every gate open, a size 2 and a size 3
  do too. The limit is 3 times the loop's length at the slowest size's
  pace. Core simulation, off-screen projection off. A case for a safety
  net (a stalled train slime, two slimes stuck in each other: chunk 23A)
  fails the run, since the net moves the slime to the start.
- **Rule 7:** from both ends of every row of sleepers, the level as the
  loop first reaches its section (`LevelStates.open_gates`: the gates
  before it open as after their baskets fired), the slime alone, made free
  and heading back, rejoins the train within 70 s (left alone, then lost).

What each rule checks by code, and what it leaves to a person:

| Rule | By code | Left to a person (`manual:`) |
|---|---|---|
| 1 | the loop closes in every gate state; switches go onward by default; laps | |
| 2 | no size filter in v1; size 2 and 3 laps | |
| 3 | every branch has a route back ending on the loop in use; the loop closes | |
| 4 | the loop's start is inside a split zone | |
| 5 | the dips found (80 px below both rims); N/A with none (the rule is a "may") | whether a dip really nudges fusion (in play) |
| 6 | a signpost within 200 px of every switch, one each, not tappable | |
| 7 | routes back only go down; the ways back | spots a free slime reaches that hold no sleeper |
| 8 | one route back per branch, starting inside it, ending on the loop | |
| 9 | a branch's sleepers (or its route back's top) peek into a settled rail view; no decoration in front covers an object or a hint | whether a hint reads as something to explore |
| 10 | every trapdoor is on the loop over its basket, the basket below | no branch or gate may need tilt |
| 11 | section 1 has 3 species, each later adds 1, within the game's 6 | |
| 12 | every gate opened by a basket's rule, one switch per basket, a gate per section but the last | |
| 13 | one return route per section, retired by that section's gate | |
| 14 | every route back still ends on the loop in use once later gates open | exploration behind a lid needs another way in |
| 15 | by construction (FrontierSets) | a set kept as landscape must not block the loop |
| 16 | at most 200 base slimes | piles mostly still (`tools/bench_level.gd`) |
| 17 | every sleeper more than 2 slime radii from the loop | |
| 18 | the nearest sleeper within 1/3 screen of the first slime | |
| 19 | every framing zone meets the loop, zoom in (0, 1]; MANUAL with none | where a wider view is needed |
| 20 | stable IDs well-formed and unique, version >= 1, sleepers numbered from .01 left to right | once released, compare IDs and migrate |
| 21 | every switch, basket and gate below the parent zone (7 mm at the reference phone's density, `TapDispatcher.parent_zone_height`, D113) in every rail view of every section's outgoing route whose width holds it, on the reference phone's 1440 × 648 screen; an object framed above the screen fails too (chunk 23E) | |

Rule 22 (b)'s numbers come from the simulation: the reach is
`FreeSlimes.max_rise(1, gravity)`, a size-3 train slime's hop top is
`2 * (ring radius + edge) + Train.hop_apex(3)`.

**On the test level** everything passes but rule 22 (b):
`s2.sleeper.15` and `.16` rest on `Dip2Hollow`, whose underside is 110 px
over the loop from x 9.93 to 10.0, outside the split zone, and whose floor
is 130 px up (a called base slime reaches 133). A size 3's hop is clipped
there by about 20 px but not stopped (the rule 2 laps pass). It is
reported, not hidden: `tests/e2e/test_level_checker.gd` lists it in
`KNOWN_BREAKS` (the test is pending until the level or the rule's reading
changes), and the checker exits 1 on the test level meanwhile.

The existing level-rule tests (`test_level_rules.gd`,
`test_level_ways_back_e2e.gd`, `test_test_level.gd`,
`test_frontier_level.gd`, `test_start_basin_e2e.gd`) call the library for
the test level, so the tests and the checker can't disagree;
`test_level_checker.gd` also breaks each rule on a synthetic level and
checks that the checker fails it.

### The scaffolder

`tools/new_level.gd -- --id=<id> [--sections=N]` (N from 1 to 4: section
1 has 3 species and each later one adds one, of the game's 6). It writes:

- `levels/<id>/level.tscn`: a skeleton, through `LevelBuilder`, that
  passes the checker (20 PASS, rule 19 MANUAL: no framing zone, rule 5 N/A:
  no dip). The start basin is the test level's (chunk 16e: the pocket
  behind the loop's start, the ramp, the terrace, the first sleeper on
  `FirstLedge` inside the split zone, the lane under the terrace: rules 4,
  18 and 22), then per section, 3.5 screens each: two bumps with two
  sleepers each, sloping to the loop; a frontier set (signpost, switch and
  trapdoor over the pit basket, quota 4; a pillar; the gate with its lid
  over the section's chute, except in the last section, whose basket's
  target is the celebration); the section's return route down its chute
  and back along a shared tunnel to the start. Species: section 1 A (the
  first slime), B, C; each later section adds D, E, F.
- `levels/<id>/fixtures/fresh.fixture.json`.
- `tests/e2e/levels/test_level_<id>.gd`, from
  `tools/new_level/test_level.gd.template`: the level loads, the full
  checker has no FAIL, 2 minutes with no input lose nothing, every fixture
  in the level's folder loads. The designer owns it and extends it.

It refuses an invalid id, `test`, an existing `levels/<id>/` or an
existing test script (exit 1: exists, 2: bad arguments, 3: a write failed,
and what it wrote is removed). It never writes gameplay code, and nothing
inside `levels/<id>/` is a script. It prints the next steps. After that,
the level is edited by hand: the skeleton is a start, not the level's
design. `tests/e2e/test_new_level_e2e.gd` scaffolds throwaway levels
(`zz-scaffold-*`) and removes them.

### Fixtures for any level

`tools/make_fixture.gd -- [--level=<id>] [--list] [name ...]` writes a
level's fixtures to `levels/<id>/fixtures/` (the folder is made if
missing); each save is loaded back before it is written. `--list` prints
`<name>: <description>` and writes nothing. The old form (`-- bump`) still
writes the test level's.

- **The test level:** its own table of fixtures and builders, as before
  (their output is byte-identical to the committed files); opening gates
  goes through `LevelStates.open_gates`.
- **Any other level** (`tools/make_fixture/level_fixtures.gd`): `fresh`
  (no save), and `gate<k>-open` for the k-th gate in loop order: the gates
  up to it open as after their baskets fired (switch inert, old slide
  entrance shut), the level otherwise as new, the camera at the start of
  the next section's loop. This is how to open the game at section N:
  `--fixture=gate<N-1>-open`.

Unknown fixtures or levels exit 1 with what exists.

### The level report

`tools/level_report.gd -- --level=<id> [--json]`: a plain-text summary for
a designer, stable and greppable, on the checker's helpers:

- the loop in every gate state: its length in screens and a size-1 lap's
  time (outgoing at the off-screen pace, return routes at the slide's
  speed);
- the population by section and species, against the 200 cap (rule 16)
  and the species rule (rule 11), with the checker's status;
- the sleeper rows (IDs, species, x span, branch);
- the exploration branches: their sleepers and their route back's length
  and time for a size-1 slime, against "left alone" (10 s) and "lost";
- the frontier sets: quota, gate or celebration, and the base slimes
  available by then;
- the framing zones (x span, zoom, offset);
- a reach estimate per row: the rise from the loop to the row's lowest
  sleeper against a called hop's reach for sizes 1, 2 and 3. A static
  estimate from a single hop (climbing in several hops isn't modelled):
  play it to be sure.

Exit 0; 2 on a bad argument or a level that doesn't load.

### Playing and looking at a level

`godot --path . -- --test-mode --level=<id> --seed=1` plays the level in a
window with the TEST MODE banner. `--fixture=NAME` starts from one of its
fixtures, `--at=<stable id>` (or `--at=x,y`) puts the camera on the rails
nearest that thing (a loop segment or a route back: its first point).
Headless, `--run-ticks=N` runs N ticks and prints the state hash.

### Level builder helpers

`tools/level_builder/level_builder.gd` (`LevelBuilder`) writes a level
scene from the components by script, x in screens and y in px: `terrain`,
`decoration`, `loop` and `segment`, `split_zone`, `first_slime`,
`sleeper_row` (numbered left to right), `branch`, `route_back`, `frame`,
`frontier_set` (signpost, switch with trapdoor, basket, optional gate
with lid), `save`. `tools/greybox_test_level.gd` is written on it; its
output is the committed `levels/test/level.tscn` except for the nodes'
`unique_id` attributes, which Godot 4.7 draws anew on every save (the
unchanged generator did the same).

## Technical choices

- **Levels by convention, not by list.** A folder and a scene are all a
  level needs; a list would be one more file for the scaffolder to edit and
  for a designer to forget.
- **The checker is a library in `tools/level_check/`, not in `src/`.** It
  is tooling: the game never runs it. It stays out of `src/sim/` (pure
  simulation) and uses the same `Level`, `LevelData`, `Camera` and
  `Simulation` the game uses, so what it checks is what the game plays.
- **The rules checker splits by theme** (`rules_loop.gd` 1 to 5,
  `rules_exploration.gd` 7 to 10 and decoration, `rules_objects.gd` 6, 12,
  15, 21, `rules_sections.gd` 11, 13, 14, `rules_placement.gd` 16 to 20,
  `rules_start.gd` 22), with the shared geometry in `level_geometry.gd`,
  the simulation runs in `level_runs.gd` and the gate states in
  `level_states.gd`, so each file stays small and tagged with the atoms it
  checks.
- **Behaviour is checked in the core simulation**, one slime alone,
  off-screen projection off: the terrain decides, and a run takes seconds.
  The whole-level, whole-session checks (DoD 1) stay in the test level's
  own tests.
- **The scaffolder reuses proven geometry**: the test level's start basin
  (rebuilt in chunk 16e for rules 1, 2 and 22) and its first frontier set,
  repeated per section, rather than new shapes that would need their own
  tuning.
- **Throwaway levels in tests**: tests that need a second level write one
  under `levels/zz-<name>-<usec>/` and remove it, with any leftover of a
  crashed run. No level other than `test` is committed: the tutorial
  (part 2) scaffolds its own.
- **Decoration builds to O96's proposed default** (D123): a `Decoration`
  component that never collides, is never a tap target and draws behind the
  level unless asked to be in front; the checker fails a decoration in
  front that covers an object or a hint.
