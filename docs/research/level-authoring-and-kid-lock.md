# Slime Train — Research Report: Level Authoring & Child-Safety Session Lock (Android, as of Sept 2026)

## A. Level authoring / level editor

### A.1 Reusing an existing editor

**Tiled (object layers, polygons, custom properties)**
- Verified: Tiled's object layer supports rectangle, point, ellipse, polygon, polyline, tile, and (as of 1.12, March 2026) capsule objects; all can carry arbitrary custom properties, and since 1.12 those properties can hold typed lists. https://doc.mapeditor.org/en/stable/manual/objects/ ; release notes https://www.mapeditor.org/2026/03/13/tiled-1-12-released.html and patch https://www.mapeditor.org/2026/05/27/tiled-1-12-2-released.html
- Verified: **Tiled has no native Bezier/curve object.** Polygons/polylines are straight-segment only. A 2016-era PR (#776, https://github.com/mapeditor/tiled/pull/776) tried an SVG-path-like Bezier tool but was never merged; the open feature request is issue #562 (duplicate target of #1150, https://github.com/mapeditor/tiled/issues/1150). The only new rounded primitive shipped is a straight-sided "capsule" (1.12), not a general curve.
- Judgment: for your curved terrain, Tiled's polylines can carry the *control points* of a curve (with a custom property like `curveType=catmull-rom`) and your engine/importer does the tessellation into a collision polygon — this is a known community workaround, not a built-in feature. Tiled also has a scripting API (JS) that could pre-bake dense polylines from a small control-point set inside the editor itself.
- Layering/z-index, templates (reusable object prototypes), and custom "types" with typed properties (Tiled's *object types*/*classes* system) map well to your gate/basket/switch/zone objects and their trigger-condition-action data. Tiled itself doesn't model behavior graphs — you'd encode "basket contains ≥5 slimes → open gate G" as custom properties/references consumed by your own game logic, not authored visually in Tiled.
- Conclusion: Tiled is a strong fit for placing objects/colliders/paths with data, weak fit for authoring genuinely curved vector terrain natively.

**LDtk**
- Verified: LDtk has no free-form vector/polygon object layer at all — only Integer-grid layers, Tile layers, and Entity layers. Entities can be freely (non-grid) positioned points/rectangles with typed custom fields, but not arbitrary polygons/curves. A years-old feature request for a "geometry layer" (polygon/ellipse/polyline objects) is still open: https://github.com/deepnight/ldtk/issues/443 ; a related per-tile-collision-shape request: https://github.com/deepnight/ldtk/issues/172. Official site: https://ldtk.io/ , layers docs: https://ldtk.io/docs/general/editor-components/layers/
- **Confirmed unfit** for your case: no curved terrain authoring, no polygon colliders. It's a strong tool if your game were tile/grid-based, which yours (curved LocoRoco-style terrain) is not.

**Rive**
- Verified: Rive is a vector design tool + runtime with State Machines (visual graphs of animation states/transitions driven by inputs) and an official Android runtime (`rive-android`, distributed via Maven, min SDK 21). https://help.rive.app/editor/state-machine , https://github.com/rive-app/rive-android
- Judgment (not directly evidenced): Rive's State Machines are a plausible fit for your *decorative procedural motion* (spinning/bobbing/flowing) and even simple *interactive object* behavior (inputs → state transitions) since it supports numeric/boolean/trigger inputs and two-way data binding between app code and the animation. However, nothing in Rive's docs positions it as a physics/collision or level-composition tool — it has no concept of Box2D-style colliders, tilemaps, or a "level" of multiple independently-collidable static shapes; it's an animation/graphics format, not a physics level format. Practical shape: use Rive (or a simpler alternative) only for the decorative-motion layer and drive its inputs from your own game/behavior logic, not as your terrain/collision authoring tool. This is inference, not documented practice — I found no case study of Rive used as a physics-game level editor.

**R.U.B.E. (Box2D editor)**
- Verified: still downloadable (paid + free versions) at https://www.iforce2d.net/rube/ ; loader library `b2dJson` on GitHub: https://github.com/iforce2d/b2dJson. Forum is read-only/dormant since ~2019-2022 (last confirmed maintainer reply Feb 2022). Built around Box2D 2.x; Box2D 3.0 (Aug 2024) was a full C rewrite with a new API, and I found no evidence R.U.B.E. or b2dJson were updated for it.
- Judgment: R.U.B.E. is well-suited conceptually (physics-first authoring: bodies, fixtures, joints, custom properties) but is effectively unmaintained and tied to legacy Box2D 2.x. Only worth adopting if your chosen engine's physics is Box2D 2.x-compatible (Defold's physics is Box2D-based; Godot uses its own 2D physics, not Box2D directly, though a Box2D GDExtension exists). Risk: adopting a dormant tool for a multi-year, DLC-extended product is a maintenance liability.

**Godot's own editor as the level editor**
- Verified: Godot 4 levels are authored as scenes (`.tscn`) in the editor, saved via `PackedScene`/`ResourceSaver`, and can be shipped as separate `.pck` files loaded at runtime with `ProjectSettings.load_resource_pack()` — the official "Exporting packs, patches, and mods" doc explicitly covers DLC. https://docs.godotengine.org/en/stable/tutorials/export/exporting_pcks.html
- Verified caveat from the docs/community: PCK-splitting has real constraints — the base game must not reference anything that only exists in the DLC pack, and a community "PCK/DLC Manager" plugin exists to help split exports (PC platforms only per its listing) — https://godotengine.org/asset-library/asset/96
- Judgment: using Godot's editor to build actual `.tscn` scenes gives you full access to Godot's native 2D curve tools (`Path2D`/`Curve2D` with real Bezier curves, `CollisionPolygon2D`, `Line2D`), full node-based composition (custom scripts on gate/basket nodes), and doesn't need any external pipeline — this is likely the *lowest-effort* path to your exact requirements (curved terrain + z-index + physics colliders + decorative animated nodes + rule-driven gates), **if you choose Godot as engine**. Trade-off: levels become code-adjacent (Godot scene files with attached GDScript), which cuts against your "should be data files, not code" DLC goal unless you keep behavior generic and data-driven (e.g., a generic `TriggerZone` node type configured entirely via exported properties, never per-level scripts) — this is achievable but requires discipline; Godot doesn't enforce it for you. Loading arbitrary untrusted third-party `.tscn`/`.pck` at runtime can execute embedded scripts — for your own first-party paid DLC this is an acceptable trust boundary (you control the content), so it's a lesser concern than if levels were community-authored.

**Defold's own editor**
- Verified: Defold's Scene Editor edits `.collection` files (game-object hierarchies), has 2D/3D modes, and (Defold 1.10.4, July 2025) gained an editor-scripting API to programmatically edit collections/tilemaps. https://defold.com/manuals/scene-editing/ , https://defold.com/manuals/editor/ , https://defold.com/2025/07/11/editor-scripting-update/
- Defold's physics is Box2D-based (this is general Defold knowledge, not from a fetched source in this session — flagged as assumption to verify against https://defold.com/manuals/physics/ directly), which would make R.U.B.E./b2dJson data plausibly reusable in principle, though I did not verify a direct Defold+RUBE integration.
- `.collection`/`.go` files are protobuf text format (human/diff-friendly) per general Defold knowledge — flagged as not independently re-verified in this session; the "File Formats" doc page (https://read.bookofdefold.com/defold-a-z/filetypes) is the primary source to check directly.

**Ogmo Editor 3**
- Verified: free, open-source (MIT), JSON-only output level editor with four layer types (Tile, Decal — free placement/scale/rotation of images, Entity, Grid/metadata). https://ogmo-editor-3.github.io/ , https://github.com/TheSpydog/Ogmo-Editor
- Judgment: Ogmo's Decal layer (free transform of images) is a reasonable match for your *purely decorative object* placement, and Entity layers with custom fields match interactive objects reasonably well — but like Tiled, Ogmo has no curve/Bezier authoring and its polygon support is limited/absent; it's a lighter-weight, more game-agnostic alternative to Tiled with a smaller community and ecosystem.

**Blender (Grease Pencil / 2D curves) exported**
- Not directly evidenced in this session (no dedicated search performed); flagged as unresearched. Blender's native Bezier curve tools are more powerful than any of the above for authoring the actual curved silhouettes, but you'd need a custom exporter (e.g., a Python add-on) to emit collision polygons + custom object metadata — effectively building your own converter pipeline on top of Blender, similar in spirit to the Inkscape pipelines below.

**Inkscape/SVG as level format (custom pipeline)**
- Verified pattern, multiple real precedents:
  - `InkscapeToLevel` (https://github.com/kribblo/InkscapeToLevel): parses `inkscape:groupmode`/`inkscape:label` for layers/naming, treats paths as collision shapes, rectangles/images as position markers, outputs a Lua table.
  - BattleMints (Joe Groff): defines a custom XML namespace (`battlemints:tripwire`, `battlemints:next-board`) directly on SVG elements, walked by a custom export script. https://duriansoftware.com/joe/using-inkscape-as-a-map-editor
  - Standard `data-*` attributes are preserved by Inkscape (SVG/XML passthrough) though I found no cited example using that exact convention — it's a reasonable inference from SVG being XML.
- Judgment: this is the most flexible option for genuinely curved vector terrain with clean bezier authoring (Inkscape's native path tool) plus custom object/behavior metadata via layers/labels/custom-namespace attributes — but 100% of the "editor" is really the *converter you build*: none of these precedents ship a mature, general-purpose SVG→game-level pipeline; every project (BattleMints, InkscapeToLevel, Redline Reaver, "Charged") wrote a bespoke exporter. This is real custom-editor-building effort, just piggybacking Inkscape for the drawing UI instead of building your own vector canvas.

**Spine / Lottie (decorative animation)**
- Not directly researched this session (time-boxed); general/inferred: Lottie is timeline-only (no interactivity/state machines) and is well suited purely for the decorative-motion layer (spinning/bobbing/flowing) if you don't need it to respond to gameplay state; Rive explicitly differentiates itself from Lottie by adding state machines and two-way data binding (confirmed above). Spine is a widely used 2D skeletal animation tool with runtimes across most engines including Godot, libGDX, and (via community ports) others — not independently verified in this session, flagged as prior/general knowledge.

### A.2 Custom in-game/web editor & genre precedent

- Verified: World of Goo's *official* level editor is a **2025** addition (May 2025, by Tomorrow Corporation/2D Boy) shipped in-game with World of Goo 2 and Steam Workshop support; the developers themselves describe it as "unpolished, unsupported... but it built all the levels in World of Goo 2." https://www.gamingonlinux.com/2025/05/world-of-goo-2-gets-a-rough-level-editor-and-steam-workshop/ — I found **no evidence** the original 2008 World of Goo used Inkscape/SVG officially; that claim traces only to a fan clone ("OpenGOO") and a third-party fan editor (GooFans), not to 2D Boy's actual pipeline. Treat "World of Goo used SVG/Inkscape" as **unverified/likely false** as stated for the official game — correct it in your planning notes.
- Verified: Cut the Rope 3's producer stated in a Paladin Studios Q&A that in-house tooling let designers iterate on levels without programmer involvement (https://paladinstudios.com/2023/11/02/qa-with-the-cut-the-rope-3-development-team/) — confirms the "custom in-house data-driven editor freeing designers from code" pattern in this genre, but gives no technical detail on the tool itself.
- Verified: Gish's original level editor was a barebones, keyboard-shortcut-driven internal tool with no placement UI (per a 2006 review) — illustrates that even successful physics-platformers shipped with minimal, unpolished internal tools; the game went open-source in 2010 so its editor code is inspectable directly if needed.
- LocoRoco Cocoreccho!'s internal tooling: **no public information found** after two search passes. The only public "editor" in the LocoRoco franchise is "Loco Editor," a *player-facing* minigame in the original PSP LocoRoco (not Cocoreccho!, and not a real level-design tool). Treat Sony Japan Studio's actual internal pipeline as **unknown/unresearchable via public sources** — Japanese-language CEDEC/developer-interview material might exist but wasn't found.
- Judgment (recommendation-level): a **hybrid pipeline — vector art authored in Inkscape or Figma, converted by a custom script into your own JSON/binary level format, with gameplay object placement either in Tiled (object layer + custom properties/templates) or a small custom placement tool** — is the most evidenced, lowest-risk-per-effort path given (a) Tiled's lack of curves, (b) LDtk's unsuitability, (c) R.U.B.E.'s dormancy, and (d) the genre precedent of always ending up building bespoke tooling anyway. If Godot is chosen as the engine, using Godot's own editor directly (scenes as levels, `Path2D`/`Curve2D` for terrain, generic data-driven trigger nodes, `.pck` DLC export) is plausibly *even lower effort* than a Tiled+Inkscape hybrid because it avoids building a converter at all — this is my judgment based on the assembled evidence, not a documented case study of this exact use case.

### A.3 Data format concerns

- **Bezier → collision tessellation**: no tool surveyed does this natively end-to-end for you except Godot's own `Curve2D.tessellate()` (general Godot API knowledge, not independently fetched this session — verify against https://docs.godotengine.org/en/stable/classes/class_curve2d.html directly) combined with `CollisionPolygon2D`. In every other pipeline (Tiled polylines, Inkscape paths) tessellation is something you must implement yourself.
- **Data-driven trigger/condition/action** ("basket ≥5 slimes → open gate"): none of the surveyed *editors* (Tiled, LDtk, Ogmo, Rive) model this as a first-class authoring concept — you always end up defining your own schema (e.g., `{trigger: "slime_count_in_zone", zoneId, op: ">=", value: 5, action: "open_gate", targetId}`) stored as custom properties/entity fields, interpreted by your own runtime logic. This is consistent across the whole survey and is a firm conclusion, not a guess.
- **Versioning for DLC**: not deeply researched this session; standard practice (general knowledge, flagged as inference) is a `formatVersion` field in each level file plus a loader that migrates older versions — none of the surveyed tools provide this for you; it's your own responsibility regardless of editor choice.
- **DLC delivery on Android — verified, and this is a load-bearing distinction**: **Google Play Billing and Play Asset Delivery (PAD) are not alternatives — you need both.** Billing (via the Play Billing Library, one-time/non-consumable `INAPP` product type) only handles the *purchase transaction*; Google's own docs state Play Billing "does not provide any form of content delivery." PAD is the free, Play-hosted asset-delivery system (asset packs with install-time/fast-follow/on-demand modes, delta patching) for the actual *files*, and explicitly carries "no executable code" — fine for data-only level packs. Sources: https://developer.android.com/guide/playcore/asset-delivery , https://support.google.com/googleplay/android-developer/answer/10281818 . Practical flow: purchase confirmed via Billing → app requests the matching on-demand asset pack via PAD → app re-verifies ownership before unlocking (since PAD delivery is decoupled from purchase-gating; your app must enforce the link, PAD does not).

## B. Child safety: session lock & timer

### B.1 Screen pinning / Lock Task Mode — verified mechanics

- **`Activity.startLockTask()`** from an ordinary (non-device-owner-allowlisted) app produces **screen pinning**, not true kiosk lock task: the system shows a mandatory "Use screen pinning?" confirmation dialog the app cannot suppress or auto-accept; while pinned, Home/Overview/notification-shade are blocked and other apps can't be launched, but **the user can always exit** via the documented gesture (hold Back+Overview in 3-button nav; swipe-up-and-hold in gesture nav — confirmed current in Google's own Android Help: https://support.google.com/android/answer/9455138), optionally gated behind the device's own PIN/pattern/password if "Ask for PIN before unpinning" is enabled in Settings.
- **True device-owner Lock Task Mode** (no user-visible exit) requires the app to be a **Device Policy Controller/device owner**, set via `DevicePolicyManager.setLockTaskPackages()`, which in practice requires enterprise/kiosk provisioning (`adb shell dpm set-device-owner ...` or a full DPC enrollment flow) — **not realistic for a consumer Play Store app**, since device-owner status generally requires the device to have no existing Google account/be provisioned before any account is added; this rules it out for "install from Play Store on a normal family phone." Docs: https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode
- The app **can detect pinned state**: `ActivityManager.getLockTaskModeState()` returns `LOCK_TASK_MODE_PINNED`/`LOCK_TASK_MODE_LOCKED`/`LOCK_TASK_MODE_NONE`, so you can build a UI that prompts the parent to enable pinning if it's not active, and re-prompt if it was exited.
- What screen pinning **cannot** block, per the same sources: the power button/lock screen, and (per general community reporting, not a single canonical doc) the status-bar pull-down for quick settings is *reduced but not always fully prevented* depending on OEM/Android version — treat this as **uncertain/OEM-dependent**, not confirmed either way in this session. Restarting the device also fully clears pinning.
- **Android 14/15/16 nuance (verified)**: Android 16 (API 36 target) makes predictive-back the default and removes the old `onBackPressed()`/`KEYCODE_BACK` dispatch path unless you migrate to `OnBackInvokedCallback`/`OnBackPressedCallback`; you should explicitly test that your exit-gate back-handling still works under predictive back once you target API 36, since this is an active, recent platform change. https://developer.android.com/about/versions/16/behavior-changes-16 . I found **no documentation describing an interaction between predictive-back and lock-task/pinning specifically** — flagged as unresearched; recommend explicit device testing.
- **Immersive mode** (`WindowInsetsControllerCompat.hide()` for system bars, with `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`) can hide status/nav bars but a user can always bring them back with an edge swipe — it's cosmetic/UX polish, not a security boundary, and doesn't prevent leaving the app. https://developer.android.com/develop/ui/views/layout/immersive

### B.2 How comparable kids' apps actually do it — verified

- **YouTube Kids**: gate is a **math question** ("For Parents Only") on unlock/settings, with an optional 4-digit-PIN alternative (per current 2026 guidance) and a **built-in session timer** (Lock icon → PIN → Timer → set minutes → Start timer). Known weakness reported at launch (2019): failed math attempts just regenerate a new question rather than locking out. Sources: SlashGear https://www.slashgear.com/youtube-kids-parental-control-lock-is-a-simple-math-question-30589281/ , Digital Trends https://www.digitaltrends.com/social-media/youtube-kids-parent-authentication-basic-math/
- **Disney+**: uses **"Kid-Proof Exit"** — the child must type back a sequence of numbers *spelled out in words* ("One, Two, Three, Four" → "1234") to leave the kids' profile; this gates *leaving the profile*, not app-external actions, and Disney+ has **no built-in session timer** — parents must rely on OS-level controls. https://help.disneyplus.com/article/disneyplus-kids-profiles
- **Pattern conclusion (well-evidenced across both)**: "parental gate" = a task the target age group is developmentally unlikely to complete quickly (arithmetic for pre-teens targeted by YouTube Kids; reading number-words for early readers on Disney+) — **for your 3–5 audience, both a math gate and a read-the-number-words gate are inappropriate**, since the target users often cannot yet do arithmetic or read; your gate needs to assume the *parent* is the one being asked, and should probably be a straightforward "hold this button for 3 seconds" / adult-literacy-requiring text prompt / simple multi-digit-entry-with-shuffled-keypad pattern (following YouTube Kids' anti-memorization shuffled-keypad idea) rather than anything a clever 4-5-year-old (who may already recognize simple digit sequences) could pass. This last sentence is my design judgment, not a cited source.
- I did not research Khan Academy Kids / Toca Boca / Sago Mini / PBS Kids individually in this session due to time constraints — flagged as a gap; recommend a follow-up pass if precise UX parity matters.

### B.3 Google Play Families / DFF policy — verified, directly relevant since your DLC is paid

- Google's Families Policies require: certified ad SDKs only, no personalized ads for children, no precise location or device-identifier transmission from children, and (for mixed-audience apps) a neutral age screen. https://support.google.com/googleplay/android-developer/answer/9893335
- **Google's own policy does not mandate a "parental gate" the way Apple's Kids Category does** — I found no explicit Google Play Families requirement for a parental gate before purchases/external links, unlike Apple's App Review Guidelines which explicitly require one for the Kids Category. This is a real, confirmed **asymmetry between the two stores** — recommend building the gate anyway (a) as good practice/COPPA-alignment, (b) to future-proof for an eventual iOS release under Apple's Kids Category rules, and (c) because it directly serves your own stated requirement regardless of store mandate.
- New (2026) **Play Age Signals API** lets developers request a parent-set age-range signal from Family Link, but it's rolling out market-by-market through 2026 (Texas/Brazil first, AU/CA mid-Aug 2026, global by end of 2026), is explicitly restricted to "age-appropriate experience" use (not ads/analytics/profiling), and only returns a coarse age band + supervision state — not a mechanism for session-locking or purchase-gating by itself. https://developer.android.com/google/play/age-signals/request-age-signals , https://android-developers.googleblog.com/2026/07/google-play-age-signals-api-safer-experiences.html
- **No public Family Link API exists for reading/writing screen-time, app-approval, or supervision controls from third-party apps** — a public Google Issue Tracker feature request for exactly this (#302210616) remains open with no indication it shipped. **Confirms your suspicion**: there is no third-party hook into Family Link/Digital Wellbeing for enforcing or reading a child's time limits from your app — you must implement your own timer entirely in-app.
- Apple equivalent (brief, for future iOS): Kids Category apps must not include purchase opportunities or external links unless behind a parental gate; Guided Access is Apple's rough analog to Android screen pinning (single-app mode, user/OS-level, requires a device passcode to exit) — general knowledge, not independently re-verified this session; check https://developer.apple.com/app-store/review/guidelines/ directly before relying on specifics.

### B.4 Timer design across app kill/restart

- Not independently sourced in this session beyond general engineering practice — flagged as inference: persist a `sessionStartTimestamp`/`sessionEndTimestamp` (wall-clock, e.g. via `System.currentTimeMillis()` and `SharedPreferences`/a small local DB) rather than an in-memory countdown, so that killing and relaunching the app doesn't reset or extend the session; wall-clock time can be manipulated by changing device date/time, so a defense-in-depth approach also anchors against `SystemClock.elapsedRealtime()` (monotonic since boot, unaffected by date changes) with reconciliation logic, and treats large backward wall-clock jumps as suspicious. No Android Digital Wellbeing or Family Link API exists to enforce or query this externally (per B.3) — the enforcement is entirely your own responsibility.

### B.5 Exposure in candidate engines — verified/inferred

- **libGDX**: your Android launcher activity (`AndroidLauncher extends AndroidApplication extends Activity`) can call `startLockTask()`/`stopLockTask()`/`ActivityManager.getLockTaskModeState()` directly — no plugin needed, it's plain Activity API. Confirmed via community kiosk examples (https://github.com/mrugacz95/kiosk) and official lock-task docs.
- **Godot 4 (Android)**: not independently verified this session for the specific Kotlin/Java plugin mechanism, but Godot's documented Android plugin system (GDExtension/Android plugin, Java singleton pattern) is the standard way to expose native Kotlin/Java calls like `startLockTask()` to GDScript — general knowledge, flagged as not re-verified against the current Godot 4 Android plugin docs in this session (check https://docs.godotengine.org/en/stable/tutorials/platform/android/android_plugin.html directly).
- **Bevy (Android via `android-activity`)**: confirmed more involved — Bevy 0.19+ requires explicitly picking `GameActivity` (API 31+, default) or `NativeActivity` (older API, but has a documented crash-on-`AppExit` quirk relevant to lock-task exit flows: https://github.com/bevyengine/bevy/pull/12095); calling Kotlin/Java APIs requires either (a) a custom Kotlin subclass of the chosen Activity type exposing helper methods invoked over JNI (pattern shown in https://github.com/snendev/admob-example), or (b) obtaining the JNI env/Activity pointer via `android-activity`'s `AndroidApp` and calling methods with the `jni` crate directly. This is a real, non-trivial "write your own small native shim" requirement — more engineering than libGDX's near-zero-effort path.
- **All three cases converge on the same underlying fact**: regardless of engine, lock-task/screen-pinning is fundamentally an `Activity`-level Android API; the practical difference between engines is only *how much shim code* you must write to reach that Activity from your engine's main loop (libGDX: none; Godot: a documented plugin layer; Bevy: hand-rolled JNI).

## Risks / Unknowns

1. **Screen pinning is not truly inescapable** — a persistent, informed child (or one who's seen an older sibling do it) can exit via the standard gesture; you should treat it as a deterrent + parental-gate combo, not a hard lock, and design your gate to still trigger on any detected exit/backgrounding.
2. **Predictive-back interaction with lock task/pinning on Android 15/16 is not documented anywhere I found** — must be verified by hands-on device testing before targeting API 35/36.
3. **OEM variance** (status bar behavior during pinning, exact unpin gesture on some devices, e.g. the Zebra device report where the documented gesture didn't match actual behavior) means you should test on multiple real OEM skins (Samsung, Pixel, budget Android), not just emulator.
4. **No verified information on LocoRoco/Sony Japan Studio's actual internal tools** — the closest genre-analog is inaccessible; treat any "how LocoRoco did it" claim as unconfirmed unless you find Japanese-language CEDEC/dev-interview material.
5. **The claim "World of Goo used Inkscape/SVG" is likely a conflation with a fan clone (OpenGOO) and should not be relied on as fact** about 2D Boy's actual pipeline.
6. **R.U.B.E./b2dJson dormancy** is a real adoption risk for a multi-year product — don't build a DLC pipeline on a barely-maintained tool without a maintenance contingency plan.
7. **Google Play Families policy specifics change frequently** (a July 2026 policy update was found mid-research) — re-check https://support.google.com/googleplay/android-developer/answer/9893335 close to your actual submission date.
8. **Time-limit tampering via device clock changes** is only partially mitigated by monotonic-clock anchoring; fully robust anti-tampering (e.g., server-verified time) is out of scope for an offline-first kids' game and represents an accepted risk, not a solved one.
9. Khan Academy Kids / Toca Boca / Sago Mini / PBS Kids session-lock UX patterns were not researched — gap if precise competitive parity is required.

## Researcher recommendations (judgment, not fact)

- **Level authoring**: prefer either (a) Godot's native editor (scenes-as-levels with `Path2D`/`Curve2D` for real Bezier terrain, generic data-driven trigger/zone node types, `.pck`-based DLC export) if Godot is selected as engine, or (b) a hybrid Inkscape/Figma-for-art + Tiled-for-object-placement-and-triggers + a custom small converter/tessellator, if a non-Godot engine is chosen. Avoid LDtk (grid-only, confirmed unfit) and treat R.U.B.E. as a fallback only, given its dormancy.
- **Data-driven behavior**: design your own small trigger/condition/action schema early (this is required no matter which editor you pick — none of the surveyed tools model it for you) and version it from day one for DLC compatibility.
- **DLC delivery**: use Play Billing (one-time/non-consumable product) for the purchase + Play Asset Delivery on-demand packs for the files, with your own ownership re-verification at unlock time — do not conflate the two systems.
- **Session lock**: implement `startLockTask()` screen pinning + your own child-unfriendly parental gate (avoid math/reading gates given your 3-5 target; prefer a shuffled-keypad multi-digit code or a hold-to-confirm pattern aimed at defeating impulsive taps) + a wall-clock-plus-monotonic-clock timer persisted across kills, and explicitly do not attempt device-owner kiosk mode (unrealistic for consumer Play distribution). Test predictive-back interaction and OEM-specific pinning-exit behavior on real hardware before shipping.
- **Engine choice impact on B**: libGDX requires effectively zero extra shim work for lock-task; Godot requires using its documented (but unverified-in-this-session) Android plugin mechanism; Bevy requires hand-written JNI shimming — factor this into engine selection if minimizing native-Android glue code matters.
