## Slime Train — Engine & Tech Research Report (evidence current as of Sept 2026)

### 1. Engines/frameworks — quick eliminations first

- **Kotlin Multiplatform/Compose custom loop**: Compose is a retained-mode declarative UI toolkit, not a game loop/renderer; you'd be building a game engine from scratch on top of a UI framework. No 2D physics, no vector-canvas game story, no accelerometer input abstraction. Fits only if you want to hand-roll everything — no evidence found that anyone ships production 2D games this way. **Dropped** — reinventing too much for a small team.
- **SDL3-based custom C/C++/Rust**: viable technically (Oboe/AAudio bindings exist, physics/vector libs pluggable) but means building your own scene graph, editor-less workflow, Android packaging, etc. Only worth it if you already have strong low-level game-engine chops. **Dropped** for a small team wanting fast iteration, but it's the fallback if Godot/Bevy prove insufficient.
- **Cocos2d-x**: unmaintained since 2019 per Cocos' own docs; **dropped**.
- **Cocos Creator**: 3.8 line is Android-capable and gets releases (3.8.8, Dec 16 2025 per [GitHub releases](https://github.com/cocos/cocos-engine/releases)) but is explicitly LTS/bug-fix-only while 4.x is only "announced," not shipped — risky to build a multi-year kids' game on a line about to be superseded. **Dropped as primary, note as fallback only.**
- **Solar2D**: alive (2026.3730, May 7 2026, MIT, Android target confirmed — [SourceForge listing](https://sourceforge.net/software/product/Solar2D/)), Lua-based, but has no built-in vector/SDF rendering story and a smaller physics/tooling ecosystem than Godot/libGDX. **Dropped** — no compelling advantage for this project's needs.
- **LÖVE2D**: latest *stable* is 11.5 (Dec 3 2023); 12.0 (the version with modern rendering work) is still unreleased as of April 2025 maintainer comments ([love2d.org forums](https://love2d.org/forums/viewtopic.php?t=96418)). Android is effectively frozen on the 2023 release. **Dropped** — stale on the platform that matters most (Android).
- **Defold**: very actively maintained (1.13.0 June 2026, Android Vulkan-by-default, targetSdk 36 — [defold.com/2026/06/22](https://defold.com/2026/06/22/Defold-1-13-0/)), Box2D built in, good Android/web/desktop export. Real candidate but: source-available (not OSS) under the Defold License, Lua-only, weaker vector/SVG story than Godot, smaller physics-plugin ecosystem for soft-body work. **Kept as a dark-horse alternative**, not deep-dived given time budget — flagged for a spike if Godot/Bevy stumble.
- **macroquad**: active (0.4.16, Jul 30 2026) but it's an immediate-mode "quick game" library, not a scene-graph engine; Android build path is manual Gradle/aapt2 work ([macroquad.rs/articles/android](https://macroquad.rs/articles/android/)), no vector/physics batteries included beyond basic shapes. **Dropped** as primary engine.

### Deep dive: the 3 realistic candidates

#### Godot 4.x
- **Android export**: mature and actively worked on; headless CLI export works (`godot --headless --export-release "Android" ...`) and is the documented CI pattern. Current stable line is 4.5 (June 2026 release, [godotengine.org/releases/4.5](https://godotengine.org/releases/4.5/)); guides already target 4.6/4.7, and Android export docs are being rewritten for 4.8 ([godot-docs PR #12328](https://github.com/godotengine/godot-docs/pull/12328)). Known rough edges: a 4.4→4.5 upgrade broke one project's Android export ([issue #108805](https://github.com/godotengine/godot/issues/108805)); a recent bug makes headless export fail if ETC2/ASTC compression is off ([issue #123504](https://github.com/godotengine/godot/issues/123504)). Toolchain must be pinned (JDK 17, matching SDK/NDK/templates) — well documented via [Android Developers' own Godot export guide](https://developer.android.com/games/engines/godot/godot-export).
- **Linux + web export**: first-class, same codebase, no rewrite needed.
- **Headless/CI testing**: GUT and GdUnit4 both run headless on Linux CI without Xvfb for most cases ([gdUnit4-action](https://github.com/godot-gdunit-labs/gdUnit4-action), [helpmetest.com guide](https://helpmetest.com/blog/godot-ci-cd-testing/)); GdUnit4 can hit input-handling headless bugs ([godot#73557](https://github.com/godotengine/godot/issues/73557)) that force Xvfb, which one user reported as unusably slow on GPU-less CI runners. Screenshot/replay testing is DIY (Godot has `Image.save_png` and deterministic fixed-`_physics_process`, but no built-in visual-regression harness).
- **2D physics**: built-in Godot Physics 2D is fine for basic gameplay but not built for soft-body pressure sims. Two GDExtension replacements exist: **godot-rapier** (actively developed, cross-platform deterministic, fluids, "1:1" API compat with Godot Physics — [godot.rapier.rs](https://godot.rapier.rs/), reviewed by [GameFromScratch March 2026](https://gamefromscratch.com/godot-rapier-physics-hands-on/)) and **godot-box2d** (appsinacup), which was explicitly paused pending Box2D v3 and its repo told users to use Rapier2D in the meantime ([github.com/appsinacup/godot-box2d](https://github.com/appsinacup/godot-box2d)) — status of a v3-based update wasn't confirmed in search. For a LocoRoco-style blob, none of these physics engines give you "soft body" for free — you'd still build a mass-spring/pressure ring yourself (see §2) using rigid points + joints/springs, which both extensions and stock Godot Physics2D can host, or skip physics-engine collision entirely and simulate the blob's own particle-spring system in a script and only use Godot physics for the level's rigid obstacles.
- **Vector rendering**: Godot bundled ThorVG (a Samsung-originated vector library) starting the same year ThorVG hit 1.0, but Godot only uses it **at import time** to rasterize SVGs into textures — SVGs are not rendered live as vectors at runtime, so they blur when scaled ([thorvg/thorvg README](https://github.com/thorvg/thorvg/)). For crisp, scalable vector art you need the community "Scalable Vector Shapes 2D" plugin (imports SVG as native Line2D/Polygon2D with generated CollisionPolygons, marked "unstable" by its own author — [godotassetlibrary.com](https://godotassetlibrary.com/asset/LnsQH8/scalable-vector-shapes-2d)) or hand-build shapes with Polygon2D/Line2D/custom `_draw()`. This is workable for your flat, curved, high-contrast art style, but expect some plugin risk.
- **Audio latency on Android**: this is Godot's weakest point for your use case. Godot's Android audio backend is still OpenSL ES, not Oboe/AAudio; a 2021 proposal ([godot-proposals#2358](https://github.com/godotengine/godot-proposals/issues/2358)) and a PR ([#86776](https://github.com/godotengine/godot/pull/86776)) to switch to Oboe exist but merge status is unconfirmed, and users on Godot 4.6 were still reporting audible latency in **March 2026** ([forum post](https://forum.godotengine.org/t/audio-latency-on-android-devices/134704)). This directly threatens tight tap-to-attract sound feedback and any in-process procedural music sync. Mitigation would likely require a custom GDExtension calling Oboe directly (no ready-made plugin found).
- **Accelerometer/tilt**: `Input.get_gravity()` / `get_accelerometer()` give a `Vector3` gravity vector directly usable to drive world/area gravity; sign convention differs Android vs iOS and isn't fully documented ([godot-docs issue #9275](https://github.com/godotengine/godot-docs/issues/9275)) — test on-device.
- **Low-end performance**: use the `Compatibility` (GLES3) rendering backend, not Forward Mobile/Forward+, on sub-$150 Android GPUs (Adreno 610/Mali-G52 have weak Vulkan drivers) per a practical April 2026 guide ([bugnet.io](https://bugnet.io/blog/how-to-test-your-godot-game-on-low-end-android-phones)); official [godot-benchmarks](https://github.com/godotengine/godot-benchmarks) track CPU/idle time but there's no ready-made low-end-Android numeric baseline in what I found.
- **License**: MIT, no royalties, healthy foundation-backed community.
- **Language**: GDScript (fast to write, adequate perf per Bunnymark-style comparisons) or C# (faster, but historically weaker on Android/mobile export tooling — not independently re-verified for 2026 here).

#### Bevy (Rust) + Avian2D
- **Android support**: works, but explicitly second-class. Bevy's own maintainers said in a Dec 2025 discussion that shipping to Android "is possible... but not easy," citing too few mobile-focused contributors ([bevyengine/bevy discussion #20998](https://github.com/bevyengine/bevy/discussions/20998)). Official `bevy_android` crate exists; community `bevy-in-app` project confirms real-device (aarch64) is the practical target since emulators only expose GLES. Bevy itself is **pre-1.0** with breaking API changes roughly every 3 months (0.18 in Jan 2026, 0.19 in June 2026) — real churn cost for a multi-year kids' game.
- **Linux + web**: strong, first-class, this is where most of Bevy's community actually ships.
- **2D physics / soft body**: **Avian2D** (0.7, tracks Bevy 0.19, Apache-2.0, ECS-native, actively maintained — [avianphysics/avian releases](https://github.com/avianphysics/avian/releases)) or **bevy_rapier2d** (wraps Rapier2D, described by Avian's own docs as "the most mature and feature-rich option" for Rust physics, with the caveat that Avian is "still young, stability issues and bugs are to be expected" — [avian2d docs](https://docs.rs/avian3d/latest/avian3d/)). Rapier2D's `enhanced-determinism` Cargo feature gives bit-identical cross-platform results (useful for replay/screenshot tests) but disables SIMD/parallel solving and costs performance — a real tradeoff for mobile ([rapier.rs/docs/user_guides/rust/determinism](https://rapier.rs/docs/user_guides/rust/determinism/)).
- **Vector rendering**: Bevy has no first-party vector renderer; the ecosystem points at `bevy_prototype_lyon` (tessellation, aging) or `bevy_vello` (wraps Vello). Vello itself has been reorganized into `vello_cpu` (mature, software), `vello_gpu` (newer, no compute-shader requirement, meant to become the production GPU path) and the original compute-shader `vello` (experimental — [linebender/vello](https://github.com/linebender/vello)). Android is not first-class for Vello: it rides on `wgpu`, and current 2026 wgpu/Android driver bugs are real (Mali render-pass flip on Pixel 9 Pro, texture-parameter segfault on Mali, Adreno WebGPU-compliance rejections). This is a genuine risk area for a Bevy+Vello Android pipeline.
- **Audio**: no built-in Oboe/AAudio path found in search; you'd be integrating `cpal`/`oboe-rs` or similar yourself. No evidence of a ready story for embedding a procedural synth here beyond what any Rust/NDK project could do generically.
- **Accelerometer**: no first-party Bevy tilt-input API found in search; would go through `bevy_android`/NDK sensor APIs directly, DIY.
- **Verdict**: technically appealing (Rust, ECS, ownership of code) but Android is the project's #1 hard requirement, and Bevy's own maintainers call mobile support rough. Pre-1.0 churn is an added multi-year maintenance cost. **Best framed as a secondary/desktop-first option, risky as the Android primary.**

#### libGDX (Java/Kotlin)
- **Status**: actively maintained, latest 1.14.2 (June 5 2026), regular Android-specific fixes shipping (r8 full-mode compatibility, ANR fix in `AndroidGraphics.destroy()`, native input rewrite — [libgdx.com/news/2026/05/gdx-1-14-1](https://libgdx.com/news/2026/05/gdx-1-14-1)). Kotlin support via the community KTX extension library, though KTX's confirmed-compatible libGDX version lagged behind (last confirmed pairing found was 1.13.1) — check before pinning 1.14.x.
- **Android export**: this is libGDX's original and strongest target platform; by far the most battle-tested Android pipeline of the three (it predates Godot as an Android 2D engine and is Google/Android-ecosystem-adjacent, e.g. referenced from Android Developers docs elsewhere).
- **Linux + web**: LWJGL3 desktop backend covers Linux; GWT/TeaVM backend covers web (heavier lift, and web is your "nice to have," not "Android is nice to have").
- **2D physics**: Box2D bound natively (JNI), the classic reference implementation, `ktx-box2d` gives Kotlin-friendly builders. Box2D v3 (rewritten 2024, 2x faster than v2.4, cross-platform deterministic since v3.1 as long as fast-math/FMA are disabled — [box2d.org/posts/2024/08/determinism](https://box2d.org/posts/2024/08/determinism/), [Box2D FAQ](https://box2d.org/documentation/md_faq.html)) is the most proven, most documented, most "shipped in real games" physics option of everything surveyed here. Whether libGDX's Box2D binding has already moved to v3 vs is still on v2.4 was not confirmed in search — worth a direct check before committing.
- **Vector rendering**: no first-party runtime vector renderer; libGDX is fundamentally a sprite/texture engine (shape drawing via `ShapeRenderer`, but that's debug-grade, not production art). You would pre-tessellate vector art to meshes/textures at build time, or write a custom SDF/metaball shader (very feasible — libGDX exposes raw OpenGL/shader pipeline access) — no Vello/ThorVG equivalent readily available.
- **Audio**: libGDX's classic strength — direct access to Android's audio stack lets you drop to Oboe/AAudio via a custom platform-specific module or NDK code much more directly than Godot currently allows, since you already own the Android/Gradle project structure. No specific 2026 confirmation found of a ready-made Oboe wrapper module, but the architecture doesn't fight you the way Godot's does.
- **Testing/headless**: libGDX's "headless" backend (`HeadlessApplication`) is a long-standing, well-known feature for running the same game logic without a GPU window — good fit for CI and deterministic-replay testing; not independently re-verified with a fresh 2026 search, flagged as a known-good libGDX feature from established documentation rather than newly confirmed here.
- **License**: Apache 2.0.
- **Language**: Java or Kotlin (via KTX) — Kotlin is a strong fit for a small, readable, kid-game codebase.

### 2. 2D physics & soft-body / blob behaviour

- **No official LocoRoco write-up exists** from Sony or the original developers — confirmed absent in search. Everything available is developer reconstructions.
- **Consensus approach** (Gish, and Gish-/LocoRoco-style clones): a **mass-spring system** — particles arranged in a ring, connected to neighbors by springs, using Verlet integration for stability, with either (a) internal/radial springs, (b) a center point, or (c) an exact area/volume-preservation constraint each frame to stop collapse ([Cowboy Programming "Blob Physics"](https://cowboyprogramming.com/2007/01/05/blob-physics/), [Gorilla Sun tutorial](https://www.gorillasun.de/blog/soft-body-physics-and-blobs/), [GameDev.net thread](https://www.gamedev.net/forums/topic/427068-loco-roco--gish-kind-dynamic-shapes/)). Softer springs are reported as *more* stable, not less — counterintuitive but stated by multiple sources. Collision detection against per-particle rings is the hard part; a common trick is "repel forces" with a slightly-shrunk collision radius rather than hard contact resolution.
- **This is engine-agnostic** — you build it yourself as a script/ECS-system on top of any of the three engines' basic 2D transform/physics primitives; none of Godot Physics2D, Rapier, Avian, or Box2D give you "soft body blob" as a built-in feature. Practical implication for merging/splitting slimes: this is naturally expressible as a mass-spring ring you can dynamically re-parameterize (spawn a second ring and redistribute particles, or merge two rings' particle sets and re-derive a new rest shape) — feasible in any of the three stacks since it's just your own simulation code, not something the underlying physics engine needs to support natively.
- **Box2D v3** (Erin Catto, rewritten 2024, [box2d.org/posts/2024/08/releasing-box2d-3.0](https://box2d.org/posts/2024/08/releasing-box2d-3.0/)) — 2x+ faster than v2.4, cross-platform deterministic since v3.1 (avoid fast-math and FMA), latest tagged release v3.1.1 (June 4 2025); a "replay viewer" mentioned on the README suggests main-branch progress toward an unconfirmed v3.2. Most proven/most widely shipped 2D physics engine in the industry bar none.
- **Rapier2D**: `enhanced-determinism` feature gives bit-identical cross-platform replay/checksums but disables SIMD/parallel solving (perf cost) and needs care with `sin/cos/sqrt` (use nalgebra's versions, not libm, for deterministic setup values) — [rapier.rs/docs/user_guides/rust/determinism](https://rapier.rs/docs/user_guides/rust/determinism/).
- **Avian2D**: younger, ECS-native for Bevy, explicitly self-described by its own docs as less mature than Rapier.
- **Jolt**: 3D-only physics engine (Jolt Physics has no 2D mode) — confirmed as an aside, not deep-researched since it's out of scope for a 2D game; excluded correctly per your framing.

### 3. Vector rendering

- **Vello**: reorganized into `vello_cpu` (most mature, software fallback), `vello_gpu` (newer, no-compute-shader path, targeted to become the production GPU renderer), and the original `vello` compute-shader renderer (experimental, moved to a `research/` folder) — [linebender/vello](https://github.com/linebender/vello). Rides on `wgpu`; 2026 Android/Mali/Adreno driver bugs are real and open (render-pass flip on Pixel 9 Pro Mali-G715 [wgpu#10057](https://github.com/gfx-rs/wgpu/issues/10057), texture-parameter segfault [wgpu#10186](https://github.com/gfx-rs/wgpu/issues/10186)). No Vello-specific "official Android support" statement found — treat as "runs, not first-class."
- **ThorVG**: used by Godot only at **import time** (rasterize-to-texture), not as a live runtime vector renderer in-engine — a common misconception worth flagging explicitly.
- **Rive**: MIT-licensed runtimes (confirmed via [Rive's own licensing docs](https://help.rive.app/runtimes/overview/android), Aug 2026), Android runtime actively released (v11.9.1/11.9.2 mid-Aug 2026), state machines supported on Android. This is a strong fit for your "decorative animated objects" (spinning/flowing background elements, gate/switch state machines) — author once in the free Rive editor, ship the runtime (no account needed to just play back `.riv` files), independent of which core engine you pick since Rive has its own Android/native runtimes. Worth prototyping regardless of engine choice.
- **Skia (Flutter/Skiko)**: relevant only if you go Flutter+Flame, which we deprioritized because Flutter/Flame's physics story (Forge2D) is strong but its vector/decorative-animation and low-level shader access for metaballs is weaker than a Godot/libGDX custom-shader approach; not deep-dived given time budget.
- **Metaball/SDF rendering for blobs**: well-documented, engine-agnostic technique — accumulate each blob-particle's signed-distance/influence field in a fragment shader over a fullscreen quad or sprite-sized quad, then `smoothstep` a threshold for a soft anti-aliased edge; extend with a synthetic surface normal (finite-difference of the field) for fake lighting. Feasible as a custom shader in Godot, Bevy, or libGDX equally — this is the recommended way to render your particle-spring blob simulation, decoupling "physics representation" (particles+springs) from "visual representation" (SDF/metaball shader), which also sidesteps most soft-body mesh-tessellation complexity. Key references: [Inigo Quilez's distance functions](https://iquilezles.org/articles/distfunctions/), [Ronja's 2D SDF Basics](https://www.ronja-tutorials.com/post/034-2d-sdf-basics/), [shud.in "From Shader to Metaball"](https://shud.in/posts/metaballs-1).

### 4. Testing & fast iteration

- **Godot**: headless CI export and headless test execution both work today (GUT, GdUnit4), but GdUnit4's headless-input workaround (Xvfb) is reported as very slow without GPU acceleration on CI runners — worth benchmarking your actual CI hardware before committing. No native visual-regression/screenshot-diff tool found; you'd wire up `Image.save_png()` + an external diff tool (e.g., pixel-diff in your CI script) yourself.
- **Bevy**: strong desktop/CI story generally (this is where most of the Bevy community's testing actually happens), plus Rapier's `enhanced-determinism` gives genuinely bit-identical cross-platform replays — the strongest determinism story of the three stacks, if you can afford the performance cost of disabling SIMD.
- **libGDX**: `HeadlessApplication` backend is an established, long-standing feature purpose-built for exactly this (same game logic, no GPU window) — the most "just works" headless story of the three, though not freshly re-confirmed with a 2026-specific search pass.
- **Tilt simulation on desktop**: none of the three engines have a documented built-in "fake accelerometer" desktop input for testing found in search — in all cases you'd abstract "world gravity direction" behind your own interface fed by either real accelerometer input (mobile) or keyboard/mouse-driven fake input (desktop), which is straightforward regardless of engine.
- **Cross-platform float determinism**: this is a real, well-documented constraint (Box2D v3 needs FMA/fast-math disabled; Rapier needs the `enhanced-determinism` feature and nalgebra math functions) — plan for it explicitly if you want deterministic replay/screenshot tests across Linux CI and Android.

### 5. Audio

- **Godot**: still on OpenSL ES for Android as of confirmed 2026 forum reports (March 2026), not Oboe/AAudio; an Oboe-migration PR exists but its merge status is unconfirmed in search, and users are still reporting audible latency on 4.6. **This is a real risk for your project** given tap-to-attract sound feedback and any planned in-process procedural music sync — plan a spike specifically testing Godot audio latency on your actual target low-end devices before committing.
- **libGDX**: no ready-made confirmed Oboe wrapper found, but its architecture (you own the Android/Gradle project) makes bolting on a custom Oboe/AAudio JNI module much more direct than fighting Godot's abstraction — practical advantage for latency-critical audio + a custom procedural synth.
- **Bevy**: no built-in Oboe/AAudio path found; would be `cpal`/`oboe-rs` DIY, same category of effort as libGDX but with a smaller community precedent for having done it on Android specifically.
- **Google's own current guidance** (Feb 2026, [developer.android.com/games/sdk/oboe/low-latency-audio](https://developer.android.com/games/sdk/oboe/low-latency-audio)): use Oboe (wraps AAudio on API 27+, falls back to OpenSL ES below), request `PerformanceMode::LowLatency` + `SharingMode::Exclusive`; flagship-device exclusive-mode round-trip latency is now ~3–8ms, shared/default mode 15–40ms.
- **Procedural music engine integration**: **libpd** (BSD, no dependencies, official Android/iOS bindings, designed for exactly this "live-patchable audio graph" use case — [PD forum thread](https://forum.pdpatchrepo.info/topic/4347/libpd-an-embeddable-sound-engine-for-android-ios-c-java-and-more)) and **FluidSynth** (LGPL, SoundFont-based wavetable synth, explicitly designed to be embedded into game frameworks since its own origin project — [FluidSynth wiki](https://www.fluidsynth.org/wiki/Applications/), Android build documented via a [step-by-step Medium tutorial](https://medium.com/swlh/creating-a-fluidsynth-hello-world-app-for-android-5e112454a8eb) and a maintained [VolcanoMobile Android fork](https://github.com/VolcanoMobile/fluidsynth-android)) are both real, embeddable options. No example was found of anyone combining the two in one game; combining libpd (control/composition logic) + FluidSynth (sample playback) feeding one Oboe/AAudio callback is a plausible architecture but is **my own suggestion, not evidence-backed** — flag as an assumption. Both are native/C libraries reachable via JNI from libGDX easily, via GDExtension from Godot with more friction, and via `bindgen`/FFI from Bevy/Rust.

### Key risks/unknowns needing a prototype spike

1. **Godot Android audio latency** — the single biggest concrete risk found in evidence (still-open in 2026); must be spiked against your actual target low-end devices before betting on Godot for a tap-timing-sensitive, music-driven kids' game.
2. **Whether libGDX's Box2D binding is on v2.4 or the rewritten v3** — not confirmed in search; directly affects performance and determinism claims you can rely on.
3. **Vello/wgpu Android GPU driver bugs (Mali/Adreno)** — open issues in 2026; if you lean on Bevy+Vello, budget time for driver workarounds or fall back to `vello_cpu`.
4. **Whether godot-box2d has resumed development against Box2D v3** — its repo said "waiting for box2c," status since unconfirmed.
5. **Soft-body blob merge/split performance at scale** — no engine gives this natively; a spike should prototype ~30-50 simultaneous particle-spring rings + SDF shader render on an actual sub-$150 Android device to validate the "near-idle, lots of slimes wandering" scenario is affordable.
6. **libpd + FluidSynth co-integration** — no prior art found; this is a genuine engineering unknown, not just an integration risk, and should be spiked independently of engine choice.
7. **CI headless testing throughput** — GdUnit4's Xvfb-based headless-input workaround was reported as very slow on GPU-less runners; verify actual CI turnaround time before locking in Godot's testing pipeline.

### Researcher's recommendation shortlist

1. **libGDX (Kotlin + KTX)** — best-supported path to your two hard constraints (native Android primary, Linux/web secondary) with the least fighting-the-framework risk: Android is its original and best-proven target, Box2D is the most proven/most-shipped 2D physics engine surveyed, `HeadlessApplication` gives a clean CI story, and its direct-to-GL/Android-project architecture makes both a custom SDF/metaball blob shader and a custom Oboe+libpd/FluidSynth audio pipeline more tractable than fighting Godot's or Bevy's abstractions. Tradeoff: no built-in vector-art or soft-body tooling — everything on those two fronts is DIY, same as with any other candidate here.
2. **Godot 4.x (GDScript)** — best editor/tooling experience, fastest iteration for non-programmers (art/level design), strongest headless-CI-plus-testing-framework ecosystem (GUT/GdUnit4), Rapier GDExtension gives a genuinely mature deterministic physics option. Held back from #1 purely because of the confirmed, still-open Android audio-latency problem — recommend only if a quick audio-latency spike on real target hardware comes back acceptable (or if you're willing to ship a custom Oboe GDExtension).
3. **Bevy + Avian2D/Rapier2D** — most interesting for the desktop/Linux/CI-determinism story (Rapier's bit-identical cross-platform replay is the strongest determinism guarantee of the three) and for teams that want Rust and don't mind pre-1.0 churn; recommend as the **secondary/desktop-first prototyping stack** (build and test the blob simulation and level logic here first, since that's Bevy's strength) while treating Android shipping as the highest-uncertainty part of this option, gated on resolving the Vello/wgpu Android driver-bug risk.

Cross-cutting recommendation regardless of engine: use **Rive** (MIT, mature Android runtime, state machines) for decorative animated objects and interactive gate/switch/basket state, and build the slime blobs as your own **mass-spring particle ring + SDF/metaball fragment shader**, independent of whichever core engine you choose — none of the surveyed engines or physics libraries provide LocoRoco-style soft-body blobs natively, and no official Sony/LocoRoco documentation of their original technique exists.
