# S20 FE phone session, both ticks (chunk 5N U8), 2026-10-06

Chunk 5N's native tick (`SlimeSolver.step`, one native call per tick) against
the GDScript tick on the reference phone. The method and windows are the
same as `2026-10-03-s20fe-session.md` and `2026-10-03-s20fe-phases.md`. It
answers the five open questions of `2026-10-05-5n-desktop-bench.md` (unit U7).
Every number comes from the PERF lines (`perf.log`) or the test-mode `STATE`
lines, never from a screenshot.

**Read this first: four of the eight runs ran on a slow phone.** Runs 3 to
6 (`stress-moving` and `s3-basket-59of60`, both ticks) are about 1.6 times
slower than the same fixtures on 2026-10-03. The GDScript behaviour, which
does the same work on both ticks, says so (see "The phone's own speed").
The thermal status stayed 0 throughout. The ABBA order put both ticks of
each fixture in the same state, so native against GDScript stays like for
like. These runs' absolute fps are pessimistic, though, and both fixtures
should be measured again before chunk 22's repeat counts them.

## Device, build and method

- **Device:** samsung SM-G781B (S20 FE, serial RFCNA0WV2AR), Android 13
  (API 33), gl_compatibility, 2400x1080, vsync on, 60 Hz,
  max_ticks_per_frame=2 (the `PERF_INFO` line).
- **Build:** the debug APK (`com.slimetrain.dev`) exported from cb7e6f5 and
  installed once with `adb install -r` (first run). It holds
  `libslime_native.android.template_debug.arm64.so` (`-O2
  -ffp-contract=off -fno-fast-math`, the same flags as the release library).
  Every run's `perf.log` header carries the game's `TICK` line: `TICK native
  (--tick=native)` or `TICK gdscript (--tick=gdscript)`. The only `E godot`
  line in each logcat is that TICK line, which goes to stderr. In the native
  runs every GDScript solver phase reads 0, so no tick fell back.
- **Runs:** `tools/android/perf.sh --serial=RFCNA0WV2AR --phase-timers
  [--no-build --no-install] --fixture=<f> --tick=<t> --label=u8b-<t>`, seed
  1, one PERF line a second. Each run lasts 5 min; `stress-still` runs 2 min
  (`--warm-minutes=2`). The census run is `--warm-minutes=0 --census`
  (60 s). The phase timers are on in every run (a few µs a tick, the same
  on both ticks).
- **Windows** (`perf_summary.py --cold=60 --warm=60`): cold = the lines
  within 60 s of the first one, warm = the last 60 s (the fifth minute,
  `stress-still` the second). Tick ms and phases are weighted by ticks. The
  fps mean is the plain mean of the lines' `fps=` fields, which the summary
  doesn't print. `tables.py` prints every number below.
- **Solver** is what 5N ports. On the GDScript tick it is the passes
  integrate, pairs, contacts, rings, terrain, doors and rest; on the native
  tick, the one `native` lap. **Behaviour** is the rest of the step,
  GDScript on both ticks.
- **Crowd detail** is as merged (D140). Chunk 22c's `auto` mode isn't built
  yet.
- **Raw logs:** `2026-10-06-5n-s20fe-session/`, one folder per run (perf.log,
  summary.txt, thermal.log; the census run adds census.txt), plus
  `hashes.txt` and `tables.py`. Each run's logcat.txt stays in the
  gitignored `build/perf/u8b-*`.

### Where the native tick's frame goes

- **`stress-dense` holds 60 fps with little room.** In the cold window a
  frame holds 1.02 ticks of 11.3 ms (11.49 ms in ticks) and 5.45 ms for the
  rest of the frame, which includes any wait for vsync. The GDScript
  tick's 15.1 ms doesn't fit in a 16.7 ms frame, so it runs about 1.8 ticks
  a frame at around 30 fps. The step from 60 to 30 fps lies somewhere
  between those two tick costs.
- **The solver is 2 to 6 % of the native step** (283 µs of 11133 on
  `stress-dense`). The rest is GDScript behaviour. The largest behaviour
  phases in the cold windows, native tick:
  - `stress-dense`: offscreen 3327, fusion 3132, train_follow 1648,
    train_steer 776, frontier 742, loop_start_queue 468.
  - `s3-basket-59of60`: offscreen 5400, train_follow 2179, frontier 1667,
    fusion 1303.
  - `stress-moving`: fusion 8894, train_steer 2455, train_follow 1909,
    offscreen 1585.
- **No crash and no freeze:** every run completed (`ended: completed`).

run 7. Neither the GDScript code nor the fixtures can explain it: the
`stress-dense` runs on either side match 2026-10-03, and these three phases

with the same crowd (25.9 and 24.6 physics slimes).

## U7's five open questions

1. **The native code's phone factor.** In the crowds the native lap's
   factor is 2.6 to 3.1 as measured. `stress-dense`, on a phone in its
   normal state, gives 3.1. `stress-moving` and `s3-basket-59of60` give 2.6
   and 2.9, measured on the slow phone, so about 1.6 to 1.8 in the normal
   state (an estimate). That matches the GDScript solver's own factor in
   the same windows (2.6 to 3.1 as measured, about 1.8 to 1.9 once the slow
   phone is taken out), so D142's factors hold for the native code in
   crowds as well as for GDScript. Measured, they sit above D142's 2.1
   cold. On a still scene the
   factor is 11.6 (22 → 256 µs; see 5). Not measured: throttled (the phone
   never left thermal status 0) and the release template. perf.sh can't
   measure a release-template build:
   - The PERF log (`src/debug/perf_log.gd`) and test mode are guarded by
     `OS.is_debug_build()`. The release preset also leaves out
     `src/debug/`, `src/test_mode/` and `levels/test/`.
   - The SlimePlatform plugin reads `slime_args` in a debuggable build
     only.
   - The release APK has no level, so even an outside probe has nothing to
     measure.

   The native library is built with the same flags in debug and release, so
   the debug APK's native lap stands for the release one. A release
   measurement would need a probe that runs in release builds, which is a
   spec decision outside 5N. The GDScript behaviour is expected to run
   somewhat faster on the release template, but that wasn't measured.
2. **The behaviour floor on the phone** (debug APK), µs per tick on the
   native tick:

   | Fixture and window | Behaviour, µs per tick |
   |---|---|
   | `stress-still` | 4803 to 4830 |
   | `stress-dense` | 9539 (warm) to 10849 (cold) |
   | `s3-basket-59of60`, section 3 | 13094 |
   | `s3-basket-59of60`, section 1 | 15186 |
   | `stress-moving`, cold | 17857 |

   `s3-basket-59of60` and `stress-moving` are slow-phone numbers. On their
   own, the behaviour phases break D138's 8 ms simulation budget in every
   crowded window, on either tick: dense is in the normal state and still
   reads 9.5 to 10.8 ms. The next step is a spec decision. Porting
   behaviour code (offscreen, fusion, train_follow, train_steer, frontier,
   the loop-start queue) is outside 5N (D158).
3. **fps in the cases that matter:** see "The numbers". `stress-dense`
   native runs at 59 fps cold and warm (GDScript: 32.8 cold). `stress-moving`
   native runs at 23.2 cold, p5 18.4 (GDScript: 13.2). `s3-basket-59of60`
   native runs at 35.7 cold. Its section 1 crowd, after 150 s, runs at 28.5
   on the native tick (warm 24.1) against 18.6 on GDScript (warm 14.6), and
   the 2026-10-03 GDScript runs read 18 to 23 there. The last two fixtures

   crowds rise above it (`stress-moving` cold 700, `s3-basket-59of60`
   section 1 829 to 1114). It is 2 to 6 % of the step, so nothing to
   optimise now.
