| O67 | Second finger: the Definition of done says every tap gets a ripple, "including taps that do nothing else", but a second touch while one finger is down is ignored (D66). | O68 | Reopening the app: "opening the app always lands in screensaver mode" contradicts sessions and bedtime surviving a kill, and the access model's "reopening resumes where it was". Which wins, per state (session, bedtime)? (ux Q37) **Proposed default (D95, pending the user's approval):** reopening resumes where it was: the app lands in the state its stored timers give. A running session resumes (wind-down included); bedtime resumes with the rest of its cooldown; if the cooldown ran out meanwhile, screensaver mode, without replaying sunrise. Screensaver mode only when no session or bedtime is running. Tilt's neutral is taken again when a session resumes. *Why:* the timers and the access model already say so, and leaving the app must never dodge bedtime. | concept |
| O69 | Which taps start a session: does a tap on the parent zone, an edge button or an object count as the first tap? If the parent zone counts, a parent opening the buttons to leave starts a 15-minute session. (ux Q38) **Proposed default (D95, pending the user's approval):** any tap that reaches the world starts the session: open ground (a call) or an object (it operates it). A tap on the parent zone or an edge button doesn't; the edge buttons still move the camera in screensaver mode. *Why:* a parent opening the buttons, or looking around, mustn't start 15 minutes, while the child's first touch of the world is play. | concept |
| O70 | Edge-button press: is one press a fixed step, or does the camera move while the finger stays down? v1 bans hold gestures, yet leaving a framing zone "takes a slightly longer push". (ux Q39) **Proposed default (D95, pending the user's approval):** a press moves the camera at least one fixed step; while the finger stays down it keeps moving at a steady pace, and eases to a stop on release. Leaving a framing zone takes holding the button a little longer (about 1 s, to try); a short press stays inside. *Why:* one button, and holding it is only a longer press, not a gesture to learn; D90 already assumes holding goes round the loop. | concept |
| O71 | First-play hint: does the 10 s count start when screensaver mode shows or when the session starts? Does deleting the level's save bring the hint back? (ux Q40) **Proposed default (D95, pending the user's approval):** the 10 s count from the first frame the world shows on a fresh save of the level (on first launch, screensaver mode right after setup), not from the session start, and count again each time the world shows while the hint is still due. The first call marks it done in the level's save, so deleting that save brings it back. Not shown during bedtime. *Why:* watching is playing, and a deleted save is a first play again. | concept |
| O72 | Deleting the running level's save: what happens to the live world and the running session, and do the hint and the celebration come back? (ux Q41) **Proposed default (D95, pending the user's approval):** the level reloads fresh at once, as on a fresh install: the hint is due again and the celebration can play again. The session or bedtime and their timers carry on untouched (they aren't part of a level's save). Deleting removes the save's backup too. *Why:* one simple result, and deleting a save can't be used to dodge bedtime. | concept |
| O73 | Forgotten code: what "forgot the code?" does on a phone with no screen lock; what happens when Android's prompt is cancelled or fails; whether the new code is typed twice. (ux Q42) **Proposed default (D95, pending the user's approval):** with no screen lock, "forgot the code?" explains that clearing the app's data in Android settings is the only way, and that it erases all progress; nothing changes. Cancelling or failing Android's prompt returns to the code prompt, with nothing changed and no wrong try counted. After passing it, the new code is typed twice, as at setup; the parent is then back at the code prompt for the action they started, with the wrong tries and any wait cleared. *Why:* no dead end, one path back, and the same double entry as setup and changing the code. | concept |
| O74 | Pinning timing: on first launch, is pinning asked before or after setup (setup explains it)? Does "each time it opens" include coming back from the background? (ux Q44) **Proposed default (D95, pending the user's approval):** on first launch, pinning is asked right after setup is completed (setup has explained it by then); on every later launch, as soon as the app opens, before the world takes a tap. Coming back from the background doesn't ask again. "Leave" closes the app, so the next open is a launch and asks. *Why:* the parent reads the explanation before Android's confirmation, and "each time it opens" (D85) means each launch. | tech-direction |
| O75 | Back gesture when pinning is declined: does it let the child leave without the code, or does the app catch it? Setup says so when it explains declining pinning. *Why:* without pinning, home and recent apps can't be caught anyway. *For the user:* the app could catch back alone (a Godot project setting, to confirm in chunk 20), closing one exit of three; not proposed, to keep one rule. | tech-direction |
| O76 | Wrong-code wait: do the count of wrong tries and the 30 s wait survive the prompt closing or the app being killed? Does "forgot the code?" work during the wait? (ux Q46) **Proposed default (D95, pending the user's approval):** the wrong-try count and the end of the wait are stored on disk, so they survive the prompt closing and the app being killed. One count for every parent button; it resets on a correct code or a code reset, and starts again from 0 after a wait. "Forgot the code?" works during the wait. *Why:* otherwise closing the prompt or killing the app skips the wait, and a parent is never stuck behind it. | concept |
